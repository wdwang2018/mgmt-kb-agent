# 检索层对比评测报告：BM25 vs 稠密向量 vs 混合

- 日期：2026-10-17
- 评测脚本：`backend/scripts/bench_retrieval.py`
- 在线 Embedding：智谱 `glm-embedding-3`，维度 **2048**（实测与声明一致，无 fallback）
- 向量库：Milvus Lite（本地文件，无需 Docker），COSINE 度量
- 语料：26 个真实知识单元（`knowledge/units/*.jsonl`），26 条 embedding + 入库耗时约 **2.5~4.6s**
- 补充轮次：同日追加混合检索（HybridRetriever）与权重调优，见「第五节」

## 一、结论速览

| 查询组 | 模式 | R@1 | R@3 | R@5 | MRR | 平均延迟 |
|---|---|---|---|---|---|---|
| **A 黄金集（12 条）** | BM25 (memory) | 1.00 | 1.00 | 1.00 | **1.000** | 0.5 ms |
| | 向量 (milvus+glm) | 1.00 | 1.00 | 1.00 | **1.000** | 269 ms |
| **B 语义改写（6 条）** | BM25 (memory) | 0.500 | 0.667 | 1.00 | **0.650** | 0.7 ms |
| | 向量 (milvus+glm) | **0.833** | **0.833** | 1.00 | **0.875** | 257 ms |

**核心结论：两组查询呈现截然不同的结果，据此可得三条判断。**

1. **在现有黄金集上，向量检索没有任何增益**（两者 MRR 均为 1.000）。原因是这 12 条评测查询**本身就嵌入了精确专有名词**（`GROW`、`SBI`、`VRIO`、`OGSM`、`BEM`、`波特五力`），而 BM25 正是词面匹配，天然满分。这属于评测集的设计特征，不是向量检索的价值主张——**不应据此得出"向量无用"，也不应据此宣称"切换有收益"**。
2. **在用户真实口吻的查询上，向量检索显著占优**（MRR 0.650 → 0.875，**+0.225**；R@1 0.500 → 0.833）。真实用户不会输入"SBI 反馈模型"，而是描述"给同事提意见时讲清楚当时发生了什么"。这正是稠密向量的价值区间。
3. **代价明确**：单次查询延迟从 **0.5ms → 约 260ms（约 500 倍）**，源于每查询一次在线 Embedding 网络往返。

## 二、B 组逐条明细（语义改写查询）

| 查询（人工改写，刻意避开原关键词） | 期望单元 | BM25 Top1 | 向量 Top1 |
|---|---|---|---|
| 下面的人一遇到问题就来问我要答案，我把活派给他们又担心出乱子 | KU-LEAD-006 授权阶梯 | ✗ LEAD-004 | ✓ **LEAD-006** |
| 辅导下属时先让他自己说出想达成什么、现在卡在哪儿，再一起想办法 | KU-LEAD-004 GROW | ✓ | ✓ |
| 给同事提意见时，要讲清楚当时具体发生了什么、带来了什么后果 | KU-LEAD-005 SBI | ✗ STRAT-003 | ✗ LEAD-011 |
| 业务还在摸索阶段，用硬性考核指标还是用更有野心的目标来牵引 | KU-STRAT-007 OKR/KPI | ✓ | ✓ |
| 怎么判断公司手里的资源能不能变成长期的竞争优势 | KU-STRAT-005 VRIO | ✓ | ✓ |
| 为什么很多战略文件写出来全是口号，看不出到底要做什么取舍 | KU-STRAT-003 好战略坏战略 | ~ 排第 2 | ✓ **排第 1** |

**典型胜例**：第 1 条查询通篇没有一个"授权"字样，BM25 的 Top3 完全落空（LEAD-004/009/STRAT-005），而向量直接把 KU-LEAD-006「授权阶梯（五级情境授权）」排到第一。这是语义召回的真实收益。

**共同失败例（须如实记录）**：第 3 条两边都未命中 KU-LEAD-005。原因核查——KU-LEAD-011「绩效面谈与低绩效处理」的要点同样包含"对齐事实（数据与事例）""反馈必须具体到行为与差距"，语义高度邻近；而查询"给同事提意见"过于泛化，缺少区分 SBI 与绩效面谈的判别信号。

但两者的**错误性质不同**：BM25 漂移到了 `STRAT-003/011/010`（完全不同的战略域），而向量的错误结果仍停留在领导力域内部（`LEAD-011/009/008`）。**向量检索即便出错，语义上也保持连贯**，这对下游生成质量更友好。

## 三、由此得出的建议：上混合检索（Hybrid）

单一路线都不完整——BM25 快且吃专有名词，向量慢但懂语义，二者失败模式互补。**推荐实现 BM25 + 稠密的双路召回 + RRF 融合**（可按 `domains`/`dilemmas` 先行标量过滤）：

- 专有名词查询命中率不下降（保住 A 组 1.000）；
- 语义改写查询收益保留（保住 B 组提升）；
- 可通过缓存查询结果 Embedding 摊薄那 260ms。

**未采纳单质切换的理由**：从 A、B 两组数据看，把默认从 BM25 直接换成稠密向量会付出 500 倍延迟代价，却在现有评测基准上得不到任何可测量的提升，属于净损失。

## 四、复现方式

```bash
# .env 中置入密钥（该文件已在 .gitignore 中）
GLM_API_KEY=<your-glm-api-key>

cd mgmt-kb-agent/backend
```

脚本自带 `.env` 加载，密钥不出现在命令行中；评测所用临时向量库落在系统临时目录，不污染仓库。

## 五、混合检索（HybridRetriever）与权重调优

首轮结论（第三节）建议「上混合检索而非单质切换」，本节即为该假设的验证——**结论是：假设方向正确，但等权实现是错的**。

### 5.1 等权 RRF 反而更差

按 RRF 标准默认值 `k=60`、两路等权（`wb:wd = 1:1`）实现后实测：

| 查询组 | 纯 BM25 | 纯向量 | 混合（等权） |
|---|---|---|---|
| A 黄金集 12 条 | 1.000 | 1.000 | 1.000 |
| B 语义改写 6 条 | 0.650 | 0.875 | **0.833** |

**混合并未同时优于两者，反而低于纯向量**（0.833 < 0.875）。逐条定位根因：查询「下面的人一遇到问题就来问我要答案…」中，BM25 把语义相近但非目标的 `KU-LEAD-009` 排到第 2，而真答案 `KU-LEAD-006` 在 BM25 中排第 4 以后、在向量侧排第 1。等权 RRF 下 `LEAD-009` 拿到两路分数累加（1/62 + 1/63 ≈ 0.0322），压过 `LEAD-006` 的单路第 1（1/61 ≈ 0.0164）——**「同时出现在两路」这一信号本身被过度奖励，而 BM25 的命中在此场景下是伪信号**。

### 5.2 稠密侧加权后混合才真正占优

按 `score(d) = w_i/(k + rank_i)` 给稠密侧加权 `wd`，实测（k=60）：

| wb:wd | A 组 R@1 | A 组 MRR | B 组 R@1 | B 组 R@3 | B 组 MRR |
|---|---|---|---|---|---|
| 1:1 | 1.0 | 1.000 | 0.667 | 1.0 | 0.833 |
| 1:1.5 | 1.0 | 1.000 | 0.833 | 1.0 | **0.917** |
| 1:2 | 1.0 | 1.000 | 0.833 | 1.0 | **0.917** |
| 1:3 | 1.0 | 1.000 | 0.833 | 1.0 | **0.917** |
| 0.5:1 | 1.0 | 1.000 | 0.833 | 1.0 | **0.917** |

参照：纯 BM25 A/B = 1.000 / 0.650；纯向量 A/B = 1.000 / 0.875。

**结论**：`wd/wb ≥ 1.5` 后，混合在 B 组 MRR 0.917 **同时优于纯 BM25（0.650）与纯向量（0.875）**，且 B 组 R@3 = 1.000（优于纯向量的 0.833），A 组维持 1.000 不受影响。1.5~3+ 为效果平台期，故默认取 `wd = 2.0` 居中。

### 5.3 最终三模式对比（默认权重 wd=2.0）

| 查询组 | 模式 | R@1 | R@3 | R@5 | MRR | 平均延迟 |
|---|---|---|---|---|---|---|
| **A 黄金集（12 条）** | BM25 | 1.00 | 1.00 | 1.00 | 1.000 | 1.0 ms |
| | 纯向量 | 1.00 | 1.00 | 1.00 | 1.000 | 333 ms |
| | **混合** | 1.00 | 1.00 | 1.00 | 1.000 | 391 ms |
| **B 语义改写（6 条）** | BM25 | 0.500 | 0.667 | 1.00 | 0.650 | 0.9 ms |
| | 纯向量 | 0.833 | 0.833 | 1.00 | 0.875 | 297 ms |
| | **混合** | **0.833** | **1.000** | 1.00 | **0.917** | 318 ms |

判定：**混合在两组上均不低于任何单路线**（A 组持平、B 组占优），混合模式成立。

### 5.4 诚实边界

- **B 组仅 6 条人工构造查询**，0.833 与 0.917 的差距约等于 1~2 条查询的翻转，**样本量小，不宜过度解读**。取 wd=2.0 的依据是「平台期内结论稳定」而非最优点拟合。
- 混合的延迟（约 318ms）与纯向量相当，未因双路召回显著变慢；但仍比 BM25 慢约 300 倍，向量侧必须走后台或加缓存。
- 测试侧已对权重机制做过**变异验证**（把 `_fuse` 中的 `self._dense_weight` 改为常量 1.0，权重相关测试立即失败），确保测试不是空转。

### 5.5 端到端装配验证（hybrid 模式，真实 GLM embedding）

经组合根 `build_context` 实测：`vector_mode=hybrid`、无降级、26 单元；语义检索「新经理怎么把活交出去又不出乱子」Top3 为 `KU-LEAD-008 / KU-LEAD-006 / KU-LEAD-001`（授权阶梯正确进入前列）；标签双路召回 `TEAM+D01` → `KU-LEAD-013 / KU-LEAD-001 / KU-LEAD-002`；`on_commit → reindex → reload` 后单元 26→27，新单元立即可检索，向量侧未失效。
